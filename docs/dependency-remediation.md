# Dependency remediation — 24 October 2026

The initial audit reported three high-severity entries from one transitive chain: `@insforge/sdk@1.5.2` → `@insforge/shared-schemas@1.2.1` → `zod@3.25.76`. [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) concerns memory exhaustion when validating oversized constrained collections; its patched range starts at Zod 4.6.6. The installed shared schemas import bare `zod`. The upstream fix is for v4; the regression test explicitly checks the v4 runtime marker, because merely installing Zod 4 would not establish remediation if a consumer switched to its legacy `/v3` module.

The current published InsForge SDK/shared-schema releases still declare Zod 3. A scoped npm override makes **only `@insforge/shared-schemas` use Zod 4.6.7**, the patched version already resolved elsewhere in the application lockfile. This is an application-specific compatibility workaround outside that package's declared dependency range, not an upstream compatibility guarantee. No audit entry is suppressed.

The installed SDK runtime consumes only `ERROR_CODES` and `oAuthProvidersSchema` from shared schemas. It reads the enum's `.options`; it does not parse database/storage payloads through the other shared-schema validators. The application uses SDK client factories and APIs and does not import those validators. Both complete module entry points load under the override. The test probes the enum only; adopting other shared-schema validators is outside this workaround because some use Zod 3-specific semantics.

`tests/insforge-dependency.test.mjs` guards the exact SDK/shared-schema versions, patched resolved Zod versions, runtime import surface, provider enum and client factories. Re-review this decision if those imports or versions change, or before adopting any shared-schema parser. Remove the override when InsForge publishes a compatible patched release. The acceptance gate also requires a reproducible clean install, clean audit, lint/typecheck/build, real development CRUD/publication/private-storage/access-isolation tests and a localhost browser check; an import probe alone is insufficient.

Acceptance passed: `npm ci --ignore-scripts` reproduced the lockfile with zero vulnerabilities; `npm audit --json` reports zero findings; lint, typecheck and production build pass. All 29 focused tests, 7 auth HTTP tests, 3 shell checks and 3 backend token checks pass. The complete development publishing suite passes real CRUD, publication, media/storage and error boundaries. The customer/staff/private-file suite passes ownership, metadata isolation, file upload/list/download/delete and genuine expired-token rejection. Both suites removed their disposable fixtures. The built-in production browser loads the owner's actual Clerk identity and private InsForge profile/address state without altering owner data. This change does not configure providers, upgrade the database schema or authorize production deployment.

The clean install additionally warns that ESLint 9.39.5 is deprecated. Although `eslint-config-next@16.4.3` permits ESLint >=9, its current React and accessibility plugins declare peer compatibility only through 9. Retain that compatible toolchain until those upstream plugins support 10; no peer check is bypassed. This is a maintenance limitation distinct from the now-clean security audit.
