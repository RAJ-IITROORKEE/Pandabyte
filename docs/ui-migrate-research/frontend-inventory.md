# Frontend inventory for the UI migration plan

26 October 2026. Planning-only source review at local HEAD `8178ce0`. This inventory supports the root-owned `ui-migrate-plan.md` and `ui-migrate-handoff.md`; it does not authorize implementation, generation, content mutation or publication. No browser actions, provider requests, private configuration reads, test execution or service changes were performed by this reviewer. Runtime contents and selected new draft versions must be established separately by the root's evidence.

The current app already has functional public, account and Admin page families. A migration should change their presentation around the existing typed components and server boundaries. Replacing pages with static draft markup would discard real search, publication, identity, validation and unavailable states.

## Source baseline and concrete gaps

Read the current scope/architecture in `README.md`, `design.md`, `plan.md` and `AGENTS.md`, the package manifest, the page/component families below, and the catalog, account, content-control, accessibility and media contracts. Source files, rather than older phase summaries, determine current capabilities. In particular, `docs/phase-3-frontend.md` contains historical role-screen and notification descriptions that have since evolved.

Three source-visible presentation gaps are relevant before choosing changes:

1. About and Contact currently render a generic `PublicPage` heading followed by `PublishedDocument` and ordinary sections. There is no page-specific About/Contact layout component; their chosen visual composition must be mapped onto existing fields without fabricating company facts or adding a second contact form.
2. Theme colors are centralized, but layout, text sizing, form treatment and spacing span `app/globals.css`, `components/storefront/page-frame.module.css`, `components/home.module.css`, `components/catalog/catalog.module.css`, `components/editorial/editorial.module.css`, `components/account.module.css` and Admin styles. A shared token/frame decision must precede parallel page restyling to avoid inconsistent overrides.
3. Admin already supports a narrow-screen modal navigation drawer, but desktop navigation is a fixed-width 280px rail. It has no collapse, resize handle, drag positioning or preference persistence. The future task must add only the requested sidebar interaction, while retaining its accessible drawer and capability filtering.

These are structural findings from source, not claims of visual mismatch with a new draft. The selected draft must be compared separately. Existing styles already include reflow, focus and reduced-motion rules; a redesign must preserve those properties.

## Data authority and hard boundaries

- `lib/editorial/published.ts` uses request-scoped React `cache()` for individual reads, validates slugs, calls published-only RPCs, and parses typed public records. `lib/catalog/published.ts` validates the catalog query again, resolves real categories, calls `published_list_products`, checks response shape/limits and parses every item. `lib/insforge/public.ts` enforces `cache: "no-store"`. Layout and public pages remain dynamic. Retain these boundaries; a visual migration does not authorize shared caching or CMS replication.
- Public lists/details use approved published projections; ordinary draft saves cannot become public because of new UI. The rich content renderer uses structured React blocks, not raw HTML or executable CMS text. `sourceReview` is private and excluded/rejected by the public projection/parser. It cannot be repurposed as public specification copy.
- `docs/catalog-source-integration.md` records 42 SKU-bearing source candidates and two missing-SKU holds outside CMS. That is documentation of authorized integration scope, not a runtime record-count assertion by this audit. Preserve existing real records and original archive bytes. No importer rerun/backfill/republication is needed for theming.
- `ProductCard` shows source-observation text, date/capture caveat and non-offer label instead of sale/availability/current-price treatment. `ProductVariantPanel` exits to an archived-source panel if an observation exists or any variant is explicitly non-purchasable. Keep this guard regardless of the selected draft's commerce UI. Operational prices/stock/discounts/tax/shipping stay unconfigured where they are currently unset.
- Card previews use `/api/media/{id}?w=960`; thumbnails use `?w=96`; main product gallery/documents request the canonical unsized media URL. Main images preserve contain framing. The media handler validates ID/size, checks publication or real staff access, validates canonical object and bytes, and rechecks publication before responding. Do not bypass it with storage/Superdesign URLs, replace original delivery with resized bytes, add image optimization that changes this contract, or publish private previews.
- Clerk remains the sole identity provider. Account APIs remain user scoped and private; Admin capabilities do not grant access to customer-private profile/addresses/files. `lib/authorization.ts` and guarded server/API handlers remain authoritative. Sidebar/link filtering is presentation, not authorization.
- The contact form keeps native required/bounded fields, actual challenge token/reset and nonce flow, disabled sending/verification states, idempotency key reuse on unknown outcomes, receipt-shape validation, rate-limit/failure feedback and persisted-submission wording. Success is not proof of email delivery. Planning requires neither real inquiry submission nor real email.
- Admin record writes/lifecycle actions retain version checks, reason/idempotency requirements where applicable, conflict reload/review, private previews, current capabilities and protected owner access. IDs stay internal to keys/URLs/API state; no user-visible raw database, Clerk subject, session, revision or numeric version copy should be added.

## Admin sidebar: current behavior and bounded improvement

Current behavior is concentrated in `components/admin/admin-shell.tsx` and `admin-shell.module.css`:

- Desktop: CSS grid `280px minmax(0, 1fr)`; sticky 100dvh rail; independently scrollable navigation; sticky topbar with breadcrumb, theme toggle and real Clerk `UserButton`; exact logo and role-filtered groups. The workspace and main use `min-width: 0`.
- Below 768px: one-column workspace, fixed rail of `min(280px, calc(100vw - 44px))`, overlay, open/close controls and 180ms slide transition. JavaScript tracks the same breakpoint. Closed drawer is `inert` and `aria-hidden`; open drawer has dialog/modal semantics, body scroll lock, initial focus, Tab loop and Escape return. Navigation/path changes close it and focus main on mobile. Reduced-motion CSS removes the transition.
- No existing resize/collapse/drag state, handle or persisted width exists. Capability context is shared with dashboard/record/operation/role screens; retaining it avoids duplicating permission logic.

Recommended bounded UI-only approach for the later implementation is a **docked desktop rail with a keyboard-operable collapse/expand control and, if the selected brief still requires resizing, a horizontal resize handle**. Mobile should retain the existing drawer. A freely floating/reorderable sidebar adds positioning, overlap, focus and persistence behavior without improving the core navigation task; it is not the recommended interpretation of “resizable or draggable.” This is a proposal, not a recorded owner choice of pixel bounds.

Before implementation, define a narrow min/default/max width that still leaves a usable content region; treat 280px as the existing default, not an approved new sizing contract. Derive clamping from viewport/content needs. A handle needs a visible focus target, accessible name/orientation/current bounds, arrow-key resizing, pointer capture/cancel cleanup and a reset path. Collapse must retain accessible link names, active state and a clear way to expand; tooltips alone cannot replace labels. Width/collapse preference, if retained across visits, is a local browser preference with malformed/storage-unavailable fallback, never a new backend field. Resizing must not leak into mobile layout or change API access.

Test resize/collapse independently from Admin form logic: minimum/maximum bounds, viewport shrink/expand, tab order, keyboard handle operation, Escape/cancel, pointer release outside the handle, content/table shrinkability, both themes, 320/768/1024/1440px and reduced motion. Keep the existing mobile focus trap/return and unsaved-record navigation guard working.

## Verification handoff and honest limits

For a later UI implementation, retain `npm run check` for lint/typecheck/production build; focused unit checks for changed nontrivial behavior; and safe existing auth/shell/security regressions as appropriate. `npm run test:unit` includes theme, navigation/copy, public-record, catalog-query/source-observation, contact-protection, account/cart and circuit geometry checks. New sidebar resize state would merit a small focused test; trivial markup should be verified in the browser instead of mirrored tests.

Full backend suites such as publishing, access fixtures, addresses, contact, cart, catalog integration and notification scripts can create/mutate fixtures or require private config. Their existence is not authorization to run them during theming. Choose the smallest already-authorized check that proves the changed boundary; do not rerun importer/publication tests or use real customer writes as visual fixtures.

Browser handoff should cover priority pages first, then each remaining family, at 320/768/1024/1440 CSS pixels in light/dark: long real product names, portrait/landscape images, empty data, source observation, no results, invalid query, unavailable service, private preview, loading and permission-denied. Check keyboard menus/drawers/focus, required/invalid forms without unnecessary submission, gallery selection and old URLs. Compare against the exact selected draft version and record deliberate data/scope differences.

Current `docs/phase-6-accessibility-followup.md` records genuine zoom, runtime reduced-motion switching and screen-reader speech as manual gates. Viewport/DOM/source inspection must not be reported as those tests. Theming does not close accessibility certification, factual/rights approval, production protection, capacity, recovery, commerce or deployment gates.

Skipped here: browser/runtime verification, provider calls, private configuration, tests and implementation. Principal risk for the later migration is losing real data/security/state behavior when translating mock-filled draft layouts; keep the existing typed boundaries and page-family reuse as the acceptance baseline.
