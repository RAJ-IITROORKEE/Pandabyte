# UI migration validation contract — planning only

26 October 2026. This is a proposed execution and evidence contract for a later explicitly authorized UI migration. No UI migration, browser session, application check, provider probe, private configuration read, fixture mutation or publication was performed for this document. Historical passes below are references, not passes for the proposed migration.

## Invariants and acceptance target

The story to preserve is approved Superdesign presentation → existing Next.js UI → existing Clerk/session and business API boundaries → existing InsForge projections → truthful UI. A visual change must not change the data authority or turn a design preview into approved content.

- Keep the exact logo, approved PandaByte tokens and selected screen versions. Keep the current owner Google session and protected ADMIN access. IDs and expected versions remain internal even when their visible presentation changes.
- Keep current published content authoritative, including editable navigation/copy and honest missing-content states. Preserve non-purchasable source observations, private staff review notes, original-media delivery, private/no-store responses and publication checks.
- Do not change schemas, migrations, RPCs, RLS, grants, roles, authentication, API contracts, upload validation, publication state, operational prices/stock or infrastructure to make a layout match. A required backend change is a separately described scope decision, not part of a UI slice.
- Do not rerun the importer, prepare/copy source assets, invent missing SKUs, add checkout/payment behavior, send inquiries/email, run load tests, deploy, or perform backup/export/copy/restore/recovery work. Preserve `products/`, CAD, `.superdesign/`, design delivery records and other-chat changes.

The historical home baseline is [Home v26](../landing-v26.md); other selected screen versions are recorded in [design delivery](../design-delivery.md), [Phase 3 Admin references](../phase-3-frontend.md) and the reference evidence. The migration plan must select an exact reference for each proposed slice. A draft URL alone does not freeze its version. An unavailable or unapproved reference is `blocked`, not permission to generate a replacement or claim a comparison.

## Small browser coverage set

Avoid multiplying every route by every control/state. Use one representative route per changed layout family at **320, 768, 1024 and 1440 CSS pixels, each in light and dark**. Each family therefore has eight reflow cases. Check remaining routes that use that family for correct content, destination and unique layout differences; expand the eight-case set only for a genuinely different layout or observed failure.

At each reflow case record document overflow, visible clipping/overlap, image decoding/containment, legible controls and text, one main H1, landmarks and state-specific status/error placement. An intentional scrollable table region must have an accessible name and keyboard access; document-level overflow is not a substitute. Record actual rendered sizes, not just the requested viewport override. Cover the opened/error state most likely to overflow, not only the collapsed or pristine page.

### Conditional draft/upload checks

When a future implementation authorization explicitly includes a bounded disposable draft/upload fixture budget, root may test save → reload → private preview through existing Admin APIs/UI. Specify the record type, test title, allowed operations, known creator, never-published condition and cleanup ownership before creating it. Confirm anonymous detail remains unavailable and public UI retains its existing content. Never test a publish/withdraw cycle under a no-publication hold.

For a changed upload widget, first exercise required-file and rejected-before-storage validation; use an actual accepted upload only when that fixture operation and cleanup are included in the budget. Preserve accepted MIME/size/pixel checks, source/alt-text handling and private/customer isolation. Do not upload source archives or owner files as test data. A read-only inspection or zero-byte rejection does not prove accepted upload/save/delete behavior. Do not force an unnecessary owner-data error just to obtain a screenshot.

No new disposable users, grants or role mutations are implied by a UI migration. If customer-versus-staff checks cannot use an already authorized safe session without displacing the owner, record that coverage as blocked and leave the owner session intact. A source-reviewed role guard is not a fresh runtime 403 pass.

## Accessibility evidence: distinguish the action from the proxy

| Check | Sufficient evidence | What must not be reported as that pass |
| --- | --- | --- |
| Keyboard/focus | Actual Tab/Shift+Tab/Enter/Space/Escape/arrow sequence, active element/focus return and visible focus; open menus/dialogs/error states. | DOM `tabindex`, handler source or mouse clicks alone. |
| Contrast | Actual computed foreground/background for changed text, disabled/error/focus states in each theme; record ratio and standard used. | Eyeballing a screenshot or contrast of only a token pair with no rendered context. |
| 200% text/zoom and 400% reflow | A controlled browser session with actual zoom/text-size control and recorded observed zoom state, followed by layout/content/interaction checks. | A 320px viewport override, unchanged shortcut invocation, or device-pixel ratio alone. These are reflow observations only. |
| Reduced-motion runtime | Actual OS reduced-motion preference enabled with the supported control, browser `prefers-reduced-motion` observed true, then circuit/marquee/entrance fallback and all controls checked. Record starting preference and restore it after the controlled test. | CSS `@media` inspection, animation pause, or runtime preference false. Media emulation, if later supported, is separately labeled emulation rather than an OS switch. |
| Screen-reader output | Human-assisted Narrator/NVDA or equivalent, actual speech/announcement results for navigation, validation, preview, upload feedback and circuit selection/clear. | DOM/AX names, heading counts, ARIA/live-region presence or automated audit alone. Do not install/enable a reader as an incidental tool change. |

[The latest follow-up](../phase-6-accessibility-followup.md) explicitly left actual zoom, runtime preference switching and reader speech open. Earlier native zoom shortcuts changed neither CSS viewport nor device-pixel ratio; supported browser capability then exposed sizing only. Re-discover available capabilities at execution time. If still unavailable, report `blocked`/`not-run` with that reason; do not carry forward a historical false pass or silently change OS preferences.

Run only the relevant focused test file(s) while editing, then the final existing unit suite once after final changes. New UI behavior with a state branch, parser, geometry or security implication needs one focused test or reproducible browser assertion that proves the behavior. Do not add tests that merely repeat CSS class names, static markup or the implementation, and do not add a second E2E toolchain.

Do **not** bulk-run all `test:*` scripts. `test:publishing`, `test:storefront`, `test:source-observations`, `test:access`, `test:addresses`, `test:roles`, `test:cart`, `test:contact` and `test:notifications` use development fixture writes, users/grants, publication, storage, inquiries or other mutation paths; existing historical authorization is not a blanket UI-migration rerun permission. `test:backend` makes direct provider RPC probes. `test:catalog-import` is read-only remotely but inspects private backend/ledger state and downloads the corpus; it is not a needed UI check. `catalog:integrate` and `catalog:prepare` are operational mutation/preparation commands. `check:import` is offline source preflight with reports, not UI validation. None is needed for this planning task.

## Performance: fixed sequential observations only

Use the existing populated probe when its prerequisites hold; use the simpler readiness probe for a smaller route baseline when appropriate. Do not run both repeatedly by habit. Establish a before baseline and one after run on the same local production mode, dataset, route set and media variants; no competing build/test process or deliberate concurrent visitor workload. Record build commit, timestamp, process mode, sample order, cache headers, decoded body bytes and header/total elapsed time. Backend development-network variability remains part of these observations.

For image UI changes, preserve full gallery/default original URL behavior and permitted 96/960 previews; do not introduce Next optimizer/CDN/shared caching to improve a score. Check the unchanged media validator's focused tests plus decoded images in the browser. A visual image change alone does not require re-downloading all 96 stored images. For animation changes, check control responsiveness, pause and fallback before claiming polish.

Gate on successful responses, preserved no-store/media boundaries, no broken assets and no unexplained payload/build-size or interaction regression. Investigate a material new result once with a stated hypothesis; do not average away failures or repeat until a favorable number appears. These sparse unthrottled samples cannot establish p95, LCP/CLS/INP, field Web Vitals, production speed or capacity for 100 simultaneous visitors. No numerical latency budget has been approved by these documents; propose one separately if acceptance needs it.

## Evidence record and failure policy

Maintain one compact record for the checkpoint with arrays of cases; do not create a screenshot for every assertion or fabricate an attachment path. Suggested committed file for a later authorized run: `docs/verification/ui-migrate-<checkpoint>.json`; screenshots/logs may remain in a bounded ignored `.bootstrap/ui-migrate/<checkpoint>/` directory. Never include tokens, headers with credentials, customer bodies, Clerk subjects, raw database/session/media IDs or private source/fixture ledgers. Use logical role and fixture aliases; any exact cleanup identifiers stay in the existing private tracker. Crop/redact account identity from shareable screenshots without misrepresenting the tested UI.

Each run records:

- `scope`, `authorization`, `baselineCommit`, `testedCommit`, timestamp/timezone, owned changed files, build mode and local origin; the exact reference URL/draft version/hash when available, and expected content/identity deviations.
- `commands[]`: exact command, exit status, actual counts, result (`passed`, `failed`, `blocked`, `not-run`, `not-applicable`) and sanitized log path or reason. No boolean pass for an unavailable command.
- `browserCases[]`: case ID, route/state/logical role, reference, requested and observed CSS viewport, theme, actions, expected/observed outcome, result, screenshot path or null and observed console failures. Evidence methods are explicit: `browser-interaction`, `http`, `source-review`, `dom-ax`, `actual-browser-zoom`, `os-reduced-motion`, `media-emulation` or `screen-reader-speech`.
- `accessibilityGates`: separate actual zoom/text resizing, reduced-motion preference and reader-speech result/reason. Store the observed runtime preference and zoom method; null means unmeasured rather than false/pass.
- `measurements`: fixed probe conditions and actual observations; omitted/blocked metrics and no capacity/Web Vitals claim.
- `dataBoundary`: operations actually attempted, draft/upload fixtures only if separately allowed, publication count (required zero), real customer/role/configuration changes (required zero), cleanup result, owner session/access retained and preferences/viewport restored.
- `failures[]`: original failure and evidence, fix/commit, bounded retest result; `remainingGates[]` with owner/capability dependency; `checkpointResult` that cannot claim full release readiness.

Stop at a confirmed broken boundary, preserve its evidence and fix the owned UI cause before advancing. Unsupported controls, unavailable references and provider failures are recorded as blocked/unverified, never passed. An observed backend defect is reported with its trigger and expected contract; do not patch backend/configuration under a UI-only scope. Do not weaken security or add fake sessions/data, request interception, runtime fake-delivery modes or public Admin bypasses for tests.

Rollback is the smallest owned source change: inspect the current diff first, then root reverts only the failing UI slice or its own local commit, preserving concurrent changes. No hard reset, blanket checkout, force-push, backend rollback, database restore or content republish. A failed/ambiguous fixture cleanup blocks completion of that write-based check; retain the private tracker, stop new writes and reconcile only proven owned fixtures through the allowed existing controls. Do not blindly retry an unknown external write outcome.
