## Public reads and data boundaries

The app reads public data through the InsForge anonymous client with `cache: "no-store"`. Published APIs and sitemap routes are dynamic and also return no-store responses. Data comes from the live route and current published-revision pointer; drafts and archived records are not part of public projections. The private `catalog_search_documents` table has RLS enabled and direct runtime grants revoked. Anonymous and authenticated runtime roles call only the granted published RPCs; the search projection itself is not a client-readable table.

The Phase 4 catalog adds a private search projection over current published products: title, slug, summary, category IDs, normalized SKU/model identifiers, a full-text vector, and publication time. Exact identifiers are normalized by lowercasing and removing punctuation. Text search normalizes separators before tokenizing, so a model suffix such as `C6-308AA547` can match the indexed model `P4X-C6-308AA547`. Publication refreshes the projection in the same transaction; drafts do not enter it. The Phase 4 migrations add model-number validation, resource collection filtering, bounded blog tag filtering, and public sitemap reads. The changes are recorded in [the storefront migration](../migrations/20261024002013_phase4-storefront.sql), [sitemap migration](../migrations/20261024002427_phase4-public-sitemap.sql), [blog-topic migration](../migrations/20261024003118_phase4-blog-topics.sql), [search-tokenization migration](../migrations/20261024004612_phase4-search-tokenization.sql), [separator migration](../migrations/20261024005646_phase4-search-separators.sql), and [page-projection migration](../migrations/20261024010135_phase4-catalog-page-projection.sql).

Catalog filters are bounded at the API and RPC boundary: query text is at most 120 characters, categories at most 20, result pages at most 48 products, and offsets at most 10,000. Price filters and sale-window decisions use canonical integer-paise prices; availability is a binary published projection and does not expose quantities. Price and availability filters apply to variants before product results are paginated. The current page-DTO migration computes variant JSON only for the returned page. No checkout reservation or stock guarantee is provided by these reads.

Sitemap RPC results contain only supported canonical published routes whose records are live and unarchived. The sitemap page size is 1,000; the RPC offset is capped at 1,000,000, and the application rejects totals above 1,001,000. This allows at most 1,001 sitemap files. Administrative, account, authentication, checkout, cart, agent, and internal content paths are excluded. Categories remain redirects and do not appear as sitemap destinations. Development `robots.ts` disallows crawling and page metadata is noindex; both are release controls and must be deliberately reviewed before public launch.

## Media and inquiry operations

Public media remains private in InsForge storage and is served through `/api/media/{id}` after a positive published-media RPC check, canonical bucket-key/UUID/size validation, byte validation, and a publication recheck. The restricted managed-storage schema does not accept the attempted anonymous grants, so this route uses the server-only `INSFORGE_EDITORIAL_STORAGE_READ_KEY` for that already-authorized object read. The key is a broad project credential: keep it only in protected server configuration, never return or log it, and rotate it if exposed. The route narrows normal application access, but a leaked key may allow broader storage reads than one published editorial file. Production storage access, key scope, rotation, and isolation still need an approved operational design.

The contact endpoint accepts bounded same-origin JSON and writes an idempotent inquiry receipt. The database applies per-email and global rate limits. `notificationStatus` remains `unconfigured`: no email/SMS provider or recipient is configured, and a receipt confirms persistence only, not notification or response delivery.

## Search-plan evidence and limits

The first 10,000-row rehearsal used synthetic rows inside a rollback-only statement without refreshing planner statistics. Its estimates were one row while the query processed 10,000. The candidate measurements were 361.571 ms for the exact identifier plan and 699.001 ms for shared text; the combined filtered RPC measured 2,057.476 ms. The shared-text fixture deliberately placed the probe term in every fixture summary. The plan's primary-key-driven joins are therefore not a reliable finding about production index selection or capacity.

Adding `ANALYZE` inside the 10,000-row rehearsal exceeded the provider's 30-second query timeout. The statement rolled back; the follow-up checks found zero fixture records and zero fixture search rows. `ANALYZE` was then run after rollback to refresh development statistics. This is a timed-out rehearsal, not a completed 10,000-row performance result.

The final bounded 1,000-row diagnostic is recorded in [phase-4-query-plan.json](verification/phase-4-query-plan.json). It observed GIN index use for identifier/text candidates where the plan considered it useful: exact candidate execution was 5.998 ms, shared-text candidate execution was 10.588 ms, and the combined price/availability/search RPC measured 47.7 ms. These are local development observations on synthetic data, not a capacity test, production latency target, or query-count guarantee. Row-count assertions establish filter correctness within their tested scope; they do not establish throughput or database sizing.

## Migration recovery and ownership

The Phase 4 migrations are applied history. Do not edit or replay them to undo a change. Root is the sole migration owner and handles new forward-only corrections through the official InsForge CLI after reviewing the linked development project and migration status. Search text is derived from current live product revisions; the separator migration refreshes existing live product projections. If search normalization or projection code needs correction later, a reviewed forward migration must update the helper/projection logic and refresh every current published product row. The page-DTO migration changes query projection behavior and does not store another product copy.

Before any destructive development recovery, stop app writes and preserve a database snapshot plus a separate manifest/copy of `editorial-media` objects. A database backup alone does not restore the media files. Preserve published revisions, inquiries, operational history, and customer data unless the owner has explicitly selected a narrower recovery. Validate a database-and-storage restore in an isolated development target before resuming writes. No production rollback, production restore, or database-plus-storage restore drill has been performed.
