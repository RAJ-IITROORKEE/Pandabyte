# Order confirmation implementation — 28 October 2026

The owner-scoped `/checkout/confirmation/[reference]` route reads the existing customer order API without creating a payment or order. A Razorpay test order is presented as confirmed only after the backend reports a paid order in processing or fulfilled status. Pending, review, failed, cancelled and simulated states remain distinct. Order lines and addresses come from the stored snapshot. Purchased-image references and receipt endpoints are not available in that snapshot, so the view uses a neutral image placeholder and offers no receipt download.

The completed simulation view links to the confirmation route. A server-confirmed paid Razorpay test result now navigates to this route after the existing purchased-cart cleanup and pending-marker handling. The handoff is covered by focused tests; it has not yet been verified as a full browser purchase journey. Browser testing so far covered an unknown reference in a separate Brave session; the successful purchase journey, foreign-owner denial, responsive themes and printing still need browser verification. The component state and owner-scoped fetch tests passed; no real charges were made by this task.

The owner signed into LottieFiles and the requested Check Rebound animation was downloaded as `public/animations/order-success.json`; its source and license are retained alongside it. The MIT-licensed `lottie-web` player is loaded only for a backend-confirmed success reached from the verified checkout handoff. A single-use, account-and-reference-scoped session marker controls presentation only; revisits, reduced motion, and loading errors show the static check. The player is disposed on unmount or reduced-motion changes.
