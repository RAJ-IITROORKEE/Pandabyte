## Overview

Connect the existing AWS/OpenCode work to the working Panda Agent web chat, using OpenCode's own execution and context features. The first usable addition is external research: when local RAG evidence is missing or insufficient, the agent can choose a relevant public search, inspect the returned evidence and produce a supported answer. The response must identify the tool and its actual sources through citations and expandable details. Search excerpts, inspected pages and approved PandaByte product passages must be clearly distinguishable.

Adopt the native capabilities in small validated sub-phases. Reuse native sessions/history, context compression, question forms, agent continuation, useful planning/todos, MCP and reviewed skills where they serve the browser chat. Do not create a competing application planner, memory system or tool loop. The application still owns identity, access, current-source checks, canonical saved answers and safe browser presentation.

The configured search integration found in source is Tavily. “Davinci” in the request is recorded as the owner's wording, not treated as evidence of another configured service. This draft proposes reusing Tavily; no new search provider is being added. Current key validity and account usage remain untested in this design stage.

## The Problem

The deployed RAG/LLM path can answer from selected local passages, but it does not run OpenCode's research loop. It cannot currently continue from a RAG miss to a native web-search call and save a tool-correlated cited answer. Existing search UI text and older operator tests do not establish that capability: the current message handler rejects enabled web search, and the native search experiment was limited to one fixed public query.

The existing native implementations also have different version and hosting assumptions. Historical AWS source uses OpenCode 2.2.5; clean local execution uses 2.2.6; an older observation-only path binds 2.2.2. A fresh AWS inventory found the lightweight replacement container and an active gateway, without a running OpenCode container. It did not prove that native OpenCode is absent from the host or broken: existing code can create it per turn. It also did not establish a ready native execution/session contract. That contract must be verified before feature activation.

Simply relaxing a flag would cross incompatible tool, accounting and saved-answer boundaries. The current native guard expects a fixed tool/call sequence; current history projection drops tool details; sessions are isolated per turn rather than demonstrated durable conversation sessions. Reusing OpenCode requires connecting these boundaries coherently, not rebuilding its features or removing validation.

## Goals

1. **First usable feature: agent-decided external research.** On an eligible public question, the native agent can identify missing local evidence, choose a useful next search action, invoke the configured service and produce a cited answer when the returned material supports it. A local answer that already has adequate evidence must not incur an unnecessary web call. Search failure, conflicting evidence and an unsupported board/revision claim must produce an honest limitation or native clarification rather than guessed facts.
2. **Traceable answers and tools.** Reuse existing citation anchors, source disclosures and activity/tool presentation. Expandable details identify the actual tool, its outcome, sources returned and sources used for the answer, with accurate provenance. Do not invent tool execution from a text statement, imply that a snippet is a fetched page, or treat chip documentation as verification of a particular board.
3. **Native session and context ownership.** Reuse OpenCode history and context mechanisms, with server-owned user/chat/session binding, restart/reconnect reconciliation and clear handling of incomplete work. Keep InsForge as the canonical customer-facing record. Do not send the same history twice, treat lossy compaction as factual memory or reissue an uncertain prompt on reconnect.
4. **Minimal native interaction and planning.** Use native question/forms and the native agent's useful planning/continuation mechanisms for missing information and next steps. Expose only the MCP tools and skills needed by the research chat. Avoid introducing general coding, shell, filesystem or unrelated automation powers merely because OpenCode offers them.
5. **Preserve the working product.** Keep current hosted RAG/direct behavior available while each native slice is tested. Preserve Clerk authorization, current source withdrawal checks, customer histories, original ledgers, receipts and unknown outcomes. Existing hosted owner testing remains uncapped at application level; do not reset or silently repurpose older native/search accounting.
6. **Measure the whole operation.** Observe every model, tool and maintenance/compaction attempt using metadata, status, latency, usage and cost. Separate local retrieval, external research, model generation and final saving. Retain the existing sub-two-second local retrieval target; do not apply it as an unmeasured promise for external research or complete generation. Keep prompts, private evidence, credentials and customer identifiers out of public logs.
7. **Validate incrementally.** Establish the exact runtime and API contract; prove native tool continuation and source publication; then adopt the remaining session/context, question/planning and reviewed MCP/skill capabilities in the dependency order established by the technical plan. Each sub-phase must leave a stable, testable build and have its evidence reviewed before dependent work proceeds. Synthetic protocol/isolation/failure tests precede live paid tests; actual hosted/browser checks precede publication of a passing sub-phase.

## Non-Goals

- Build a new agent engine, planner, memory database, search vendor integration or another authentication system.
- Import the dirty original checkout wholesale, upgrade OpenCode implicitly, rewrite the selected UI, change the logo/theme or replace the working local RAG data/index.
- Enable unrestricted web navigation, arbitrary browser-supplied MCP/skill commands, shell execution, compilation, flashing, device control or autonomous commerce.
- Add image/diagram processing, bulk crawling, web indexing, visual/vector memory or third-party-content retention in the first text research slice.
- Export private submissions, account data, credentials or complete private chat history as search queries; allow retrieved text to grant tools or instructions.
- Delete/replay an old unknown turn, reset historical ledgers or treat a healthy host/mock fixture/API catalog as proof of a successful live native answer.
- Promise perfect memory, automatic claim entailment, zero provider failures or a maximum full-answer latency without measured evidence.

## Technical Plan

### Selected reuse boundary

Use the existing AWS custom ARM64 image, immutable ID `sha256:bbcbbcf6fd524caefa0063d6334e31889153e2c492713cf7f87e6eeb1cce33df`, as the starting native execution image. A disposable, network-disabled, read-only version probe verified **OpenCode 2.2.5** in this image and in the cached upstream image on 10 November. The probe needed writable temporary directories; neither the existing gateway nor its configuration was changed. Keep the separate 2.2.2 observation and 2.2.6 Windows execution profiles unchanged. Extend the existing bounded native HTTP adapter for the explicitly selected 2.2.5 path instead of replacing OpenCode with another engine or upgrading it as a side effect.

OpenCode owns native sessions, prompt admission, tool continuation, native question forms, todos, skill loading and compaction. PandaByte supplies authentication, durable ownership/admission/provenance, guarded egress and presentation. New application records describe ownership and outcomes; they do not store a second copy of the native planner or generate a competing sequence of agent steps.

Keep the working direct RAG route available throughout rollout. Add a distinct native-research route/profile with explicit per-chat execution binding; preserve historical status/cancel routing to the journal that originally admitted each request. Do not change a pending request's engine. Introduce native research for new bound test chats first, so no legacy history is silently migrated or inserted twice. Native saved sessions become execution context; InsForge remains the canonical customer-visible chat/evidence record.

### Research and external evidence

Reuse the existing Tavily adapter's public-query, bounded-body and safe-URL rules and the existing native MCP/host-broker pattern. Use a small server-owned MCP catalog with the individually permitted search tool, then the reviewed local-RAG tool. The model chooses whether a search is needed and the next public documentation query; the broker independently checks the active run, query/privacy scope, current access and durable tool-call receipt before a provider request. It returns bounded exact source excerpts with opaque source handles. No private RAG content or full private history becomes a search query by default.

Do not enable a second Tavily path: tagged OpenCode 2.2.5's built-in websearch can fall back to keyless requests and has different limits. Deny that alternate egress/tool in the initial broker-backed profile. This reuses native MCP and Tavily's existing application adapter rather than implementing another agent loop or search vendor. Exact source handles and tool-call associations remain the authority for citation publication; native text claiming a search ran is insufficient.

Source disclosures distinguish current approved PandaByte passages, Tavily excerpts and any separately verified fetched pages. The initial search slice returns excerpts; it must not label them fetched pages. The saved tool/source projection records returned and used source relationships. Validate every published quotation against the exact admitted evidence, recheck local source withdrawal and access before context delivery and final saving, and keep unsupported exact-board facts as limitations even if chip documentation exists.

### Owned sessions, restart and context

Add separate durable native-research session/run records; do not reuse a legacy per-turn table's unique native-session column for multiple turns. Bind subject/chat/native session, runtime generation, selected immutable profile and admitted message ID server-side. Allow one active native operation per bound chat, with cross-journal admission exclusion. Native IDs and directory headers are not customer authorization credentials.

Browser reconnect reads the existing owned operation and native state; it never resends the prompt. Native 2.2.5 itself resumes claimed executions after a process restart. Therefore provider and MCP egress require durable attempt fences across generations, not just a no-resend frontend rule. Preserve an uncertain attempt as unknown and deny another charged dispatch. A settled identical attempt may be recovered only from its stored verified receipt/result under the same binding; it must not call the provider again. Ordinary retries and maintenance/recovery requests use the same egress authority.

Native forms are in-memory. Browser reconnect to the same generation can list/get/reply to the existing form. On native generation change, mark an old pending form unavailable/interrupted, preserve its display/audit record and never silently recreate or answer it. A form reply/cancel must match the current owner, session, run, assistant/tool association, generation and its one-time reply claim.

Use native compaction only after its synthetic maintenance/restart tests pass. Do not implement another summarizer. Correlate compaction separately from primary steps and account all actual HTTP attempts, including title, malformed-summary correction and context-overflow recovery. Supply a server-created title to avoid unnecessary automatic title work; do not infer from that alone that all maintenance calls are disabled. Native summaries are not product evidence. A source authorization/version change retires affected execution context before another prompt; previous native memory cannot authorize withdrawn evidence.

### Minimal interaction and UI

Reuse citation anchors, source `<details>`, activity and saved tool cards. Add validated native tool identity/state/source links, native question fields and the latest completed native todo list. Do not display raw reasoning, arbitrary native metadata, provider errors or commands. Todo state comes from native tool metadata, with no application planner. Allow only reviewed local skill IDs/instructions and MCP/tool IDs; skill text does not grant permissions. Keep coding Plan-mode filesystem behavior, child agents, unrestricted shell/browser/filesystem tools and remote skill downloads outside this read-only research profile.

### Per-call policy and observability

Retain strict model/provider privacy and current access/source checks. A native research turn can have several legitimate model/tool/maintenance calls; use new per-attempt records rather than spending a one-call direct receipt several times. Keep the original native/search ledgers and unknown histories intact. Hosted owner testing remains free of a cumulative application spending cap; bounded contexts, requests, tool counts and verified receipts remain execution guards. Do not infer that an agent step limit alone bounds every charged request.

Every outbound model/tool request gets an independent private correlation record, kind, active native turn/step/tool binding, request digest, claimed/settled/unknown status, numeric latency and usage/cost. Metadata-only LangSmith observations must cover actual calls and preserve the current privacy setting. Local retrieval timing is reported separately from search, native execution and final publication. Public diagnostics contain no prompts, results, credentials or customer/native identifiers.

## Alternatives Considered

- **A new application planner/memory/agent loop:** rejected by the owner's explicit reuse direction. Existing native continuation, history, forms, compaction and MCP supply these mechanisms.
- **Upgrade AWS to the clean local 2.2.6 profile first:** not selected. The verified existing AWS image is 2.2.5, and native retry/flag/compaction behavior differs between tags. Align the thin adapter with the existing reviewed image; any upgrade is a separately tested change.
- **Relax old one-turn journals and their terminal predicate globally:** not selected. It would change recovery and source/accounting semantics of historical turns. Add a separate multi-turn research boundary and preserve existing journals.
- **Enable built-in Tavily directly with unrestricted native egress:** not selected for the first slice. The built-in keyless fallback and limits do not match the existing host-only credential/query/receipt controls. Reuse the MCP/host-broker pattern and deny alternate search egress.
- **Copy the complete dirty original AWS source tree:** not selected. Reuse only named reviewed files/patterns, with exact new phase write boundaries and tests. Unrelated original changes and private artifacts stay local.

### Transcript contract

Use tagged message IDs and finite nonnegative millisecond times. Accept at most 200 messages and 1 MiB serialized input, unique message IDs and nondecreasing created times. Validate the requested message ID/hash; find that exact user message, then restrict correlation to its suffix. Earlier completed turns cannot settle it, and another user message in that suffix makes the result unknown rather than adopting a steered prompt. Only a final idle marker agreeing with the inactive session outcome can settle it. Session creation and terminal idle must bracket the user/step times; the final marker must be at or after the latest busy time, including a native resumed execution. Missing/currently active state returns pending, not a saved answer.

Return a discriminated result: pending or unknown; terminal failed/interrupted with no answer; or terminal succeeded with answer text and private tool/compaction/todo projections. The allowed-tool argument is a server-owned readonly string list, at most16 unique identifiers matching `[A-Za-z][A-Za-z0-9_-]{0,127}`. Validate text as well-formed UTF-16 and measure serialized byte bounds before projection. Each text/tool content is at most24000 UTF-8 bytes, at most128 content parts per assistant and16 tool records per current turn. Tool input JSON is finite, acyclic, plain JSON with depth at most12, arrays/object entries at most128 and at most24000 bytes. A tool ID is nonempty, at most256 printable ASCII characters; uniqueness is scoped to `(assistantMessageID,toolID)`. Only text content is accepted for this text-research profile; file/media results are unavailable. `executed` is not independent broker execution proof; final provenance validation in later phases still requires the matching durable tool receipt.

The successful suffix may contain multiple assistant steps and compaction/skill/system activity. Each assistant step must be completed without error/retry; tool parts use the native `streaming|running|completed|error` states, exact assistant/tool identity and bounded text-only content. Allow only the caller's immutable server-owned tool-name set; unknown tools and file/media content fail closed. All tool inputs are bounded private JSON values, not public display data. Drop raw reasoning/native/error details. Permit bounded metadata projection only for native todos and correlation needed by later broker validation. A terminal answer requires all its tool states settled and a final nonempty text assistant after any tool-only intermediate steps. Return answered text, bounded tool records and compaction/todo state for later evidence/receipt validation; do not claim that this alone validates sources or settles provider costs. Failed/interrupted idle states return explicit terminal outcomes, not their text as a successful answer.

### Native question contract

Accept only a native `frm_` question whose session, generation and `metadata.kind=question` / tool assistant-message/call identity match the trusted current run. Reject global elicitation/auth forms. Support one to eight unique `q0`…`q7` fields of string or multiselect type, at most eight options per field, optional custom answers and required fields. Field title is at most300 characters, description at most1000, option label/value at most200 and option description at most500. All text must be well formed. Reject hidden, external, conditional, pattern, format or unsupported field properties/types rather than rendering semantics the UI does not implement. Allow field keys only `key,type,title,description,required,options,custom,minLength,maxLength,minItems,maxItems`; size limits must be integer, ordered and within0…2000 for string lengths or0…8 for selections. Preserve pending/answered/cancelled state without raw unrelated metadata. Check reply keys against displayed fields, required nonempty values, option membership/custom policy, uniqueness/multiselect limits, string length at most2000 and a4000-byte serialized total bound. No truthiness coercion of answers. A runtime generation mismatch returns an explicit unavailable result; do not answer, recreate or replay the old form. The trusted binding supplied to the parser contains sessionID, expected/current generation, assistantMessageID and toolID; the raw form does not assert its own generation.

### A contract freeze after initial Goldfish findings

The first two readiness reviews found Major ambiguities in exact projection shapes, state-specific handling and native Form.Info versus Form.Detail. The following contract replaces any looser wording above.

**Private result shape.** `projectResearchTurn(expected, session, active, messages, allowedTools)` returns exactly `{state:'pending'}`, `{state:'unknown'}`, `{state:'terminal',outcome:'failed'|'interrupted'}` or `{state:'terminal',outcome:'succeeded',text,tools,compactions,todos}`. `expected` is exactly `{messageID:string,promptHash:64-lowercase-hex}`. The existing `NativeSessionState` shape supplies session outcome/time; `messages` are raw tagged native message objects. Return no partial text/tools on pending/unknown/failed/interrupted. Final `text` concatenates only text parts of the last assistant, at most24000 UTF-8 bytes; ignore intermediate assistant prose. The final assistant must have native finish='stop', nonempty text and no tool part. Earlier steps can include text plus tools; their prose is not the final answer.

Each returned settled tool is exactly `{assistantMessageID,id,name,status:'completed'|'error',input,content:string[],time:{created,ran?,completed}}`. Input is a private plain JSON object; content is the completed tool's one-to32 text items, at most24000 bytes combined. Error-tool content is always an empty list; omit error/native/metadata details. Streaming tools require a bounded string input, running/completed/error tools require an object input. All tool timestamps are finite nonnegative numbers: created is within assistant lifetime, optional ran is at/after created, completed is present for settled states and at/after ran-or-created and at/before assistant completion. Streaming/running need not have completion times. Duplicate `(assistantMessageID,id)` is unknown, even if contents match. A tool error is settled and can be followed by a native final limitation; later evidence validation still determines whether any cited answer is supportable.

Each returned compaction is exactly `{id,status:'completed',reason:'auto'|'manual',created}`. Never project summary, native replay, model, cost, token, error or other metadata from it. For a successful terminal turn, every current compaction must be completed. Failed/running compaction makes inactive success unknown; an active session remains pending. Failed/interrupted native outcomes can settle without exposing any partial compaction/tool/answer data.

`todos` is exactly the latest completed allowed tool named `todowrite`'s `state.metadata.todos`, with at most20 items exactly `{content:string,status:'pending'|'in_progress'|'completed'|'cancelled'}` and nonempty well-formed content at most500 characters. Choose the greatest tool completion timestamp; break ties by later native message/content order. Missing/malformed todos on a completed todowrite makes inactive success unknown. Do not retain any other tool metadata; do not infer or generate a todo list.

**Decision order.** Validate input bounds, base message IDs/types/times, unique IDs and nondecreasing creation times first; malformed input is unknown even if active. Base-only validation of older prefix records does not publish or authorize their contents. Find the exact current user and verify its SHA-256 text hash. A missing user is pending only while active or outcome is absent; otherwise unknown. Any later user is unknown. The current suffix permits assistant, idle, compaction, synthetic, system and skill records; shell, agent/model/location switches or unknown tags in that suffix are unknown. Initial agent/model/location selections in the older prefix are allowed but never projected. Validate each suffix tool/content shape; omit reasoning/native/error/unknown metadata. Then active or absent-outcome is pending. Otherwise require a final idle agreeing with outcome, after the current user, no intervening idle, and valid session/assistant/tool completion bounds. Native busy may be later than user creation after restart; do not reject solely for that. Require session.created<=busy<=idle<=updated, final idle message.created<=session.idle, and user/step times<=idle. Failed/interrupted returns only its terminal outcome. Succeeded requires at least one completed error-free/retry-free assistant, all tools/compactions settled as above, and the final stop/text assistant. This correlation never authorizes native restart or provider replay; the later egress fence remains mandatory.

**Question signatures.** `parseResearchQuestion(rawDetail, binding)` returns `{state:'invalid'}`, `{state:'unavailable'}` or `{state:'available',question}`. It accepts raw **Form.Detail**, never a bare Form.Info or a `{data:...}` HTTP wrapper. Binding is exactly `{sessionID,expectedGeneration,currentGeneration,assistantMessageID,toolID}`; generation values are64 lowercase hex, IDs use the existing native ID format with frm_ for forms and msg_/ses_ for messages/sessions. Invalid binding is invalid; valid unequal generations are unavailable, with no form content. Validate a maximum32768-byte raw detail, title at most300 characters, matching session, native form ID, metadata.kind='question' and metadata.tool exactly identifying the bound messageID/id. Ignore other bounded top-level metadata instead of projecting it.

An available question is exactly `{id,sessionID,title,assistantMessageID,toolID,fields,state}`. Fields are normalized copies of the explicit field allowlist above; option values must be unique and type-specific length/item properties cannot appear on the other field type. `custom` and `required` default false; string options preserve absence (free text) versus an explicitly present closed list, while multiselect options are required/nonempty. Default string limits are0…2000; default multiselect limits0…8. Question state is exactly `{status:'pending'}`, `{status:'answered',answer}` or `{status:'cancelled'}`; omit cancelled messages and arbitrary metadata. Validate stored answered answers with the same value/key/size rules as a fresh reply, using an internal state-independent check. Reject unknown state or a missing Detail.state.

`validateResearchAnswer(question, rawAnswer)` returns a copied validated answer object or null. It accepts only a normalized available question with state pending; terminal answered/cancelled questions cannot be replied to. Answer keys must be a subset of displayed field keys; reject missing/empty required fields, wrong types, duplicate multiselect values, unlisted values when custom=false and violated length/item bounds. Optional omitted values remain omitted; empty optional values are allowed only when size constraints permit. Enforce at most2000 characters for custom strings/items and4000 UTF-8 bytes for the serialized answer. Never coerce primitives or echo unrelated keys. This helper does not perform a native mutation or a durable reply claim.

**Implementation-review corrections:** preserve the native distinction between an absent string-options property (free text) and explicitly present closed options (every supplied value, even an empty optional string, must be listed unless custom=true). Normalized string options remain optional; multiselect still requires options. Default only absent properties, never explicit null. Require literal enum/type strings. Plain JSON arrays must have Array.prototype, so inherited serializers/iterators are not executed. A terminal idle must be at/after the latest busy time; tool ran, like created/completed, must fit its containing completed assistant lifetime. These corrections are covered by source-review regressions and incorporated into the active contract above.
