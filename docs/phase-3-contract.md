# Phase 3 implementation contract

24 October 2026. The owner authorized editable administration/publishing, Luna xhigh workers, real built-in-browser verification and a local commit before advancing. Target is the existing linked development project; no production provisioning/deployment or paid branch is included. Root owns migrations, integration and the commit. UI-chat artifacts remain untouched.

## Agreed boundaries

- Clerk remains the identity authority. All private reads and application writes use fresh user-scoped InsForge clients. One reviewed exception serves already-published editorial bytes: the server-only media route checks the anonymous published projection, validates a canonical editorial key and size, downloads with a server-only credential, and checks publication again before responding. Restricted InsForge Cloud migrations cannot grant anon access to its managed storage schema; the key never reaches the browser, DTOs or logs, and this path has no write operation. See [the platform limitation](phase-3-operations.md).
- Draft editing requires `catalog.edit` for products/categories, otherwise `content.edit`. Publishing additionally requires `content.publish`. Stock adjustments require `orders.manage`. New least-privilege capabilities `media.manage` and `inquiries.manage` protect those modules. Existing users gain no capabilities automatically; fixture grants are temporary and the owner's customer remains unchanged.
- Bounded typed editorial records share lifecycle machinery, not an unrestricted table editor. Kinds: `product`, `category`, `blog`, `page`, `faq`, `team`, `navigation`, `contact`, `solution`, `resource`, `video`. Each kind has its own field validator/editor. Rich content is an allowlisted block document rendered as React text/elements, never executable HTML.
- `cms_records`: UUID, kind, title, slug, draft JSON, monotonically increasing version, nullable published-revision pointer, archive marker and server actor/timestamps. `cms_revisions` are immutable snapshots. List queries omit large bodies and are bounded/searchable. Catalog variants/SKUs, product-category links, price history and inventory/movements are normalized.
- Saving locks the record and requires `expectedVersion`; stale writes return409. Publish validates and atomically creates a revision/live route. Restore copies a revision into a new draft and never silently publishes. Unpublish/archive removes public visibility atomically. Prior slugs resolve through owned redirects only while the destination remains published.
- Public reads and previews are initially `no-store`; private preview also requires the corresponding edit capability and is noindex. There is no shared cached copy to invalidate or silent invalidation job to lose. Later caching must add tested invalidation/withdrawal before enabling it.
- Prices use integer paise, a nullable regular price until configured, and one optional sale interval `[from,until)`. A sale cannot exceed regular price. Price changes are explicit operational actions with audit history, independently of prose publication. Inventory changes are locked, nonnegative and idempotent by request UUID with a reason; reservation/payment workflows remain later phases.
- New media uses separate storage and metadata from private customer text files. Draft media must remain private until deliberately published. Only validated image bytes and approved document formats are accepted; referenced assets cannot be deleted. Original logo is unchanged.
- Inquiries are private, persisted before receipt, versioned for staff notes/status and isolated by their capability. Notifications remain visibly unconfigured until an owner-selected provider/recipient exists; a durable pending record must preserve the inquiry. No fabricated email delivery or retention commitment.

## Shared record transport

Module routes: `/api/admin/products`, `/categories`, `/blog`, `/pages`, `/faqs`, `/team`, `/navigation`, `/contact`, `/solutions`, `/learn`, `/videos`; detail `/{id}`, action `/{id}/{publish|unpublish|archive|restore}`. All modules map to closed kinds and validated DTOs. GET list accepts bounded `q`, `limit`, `offset`; response `{items,total}`. Detail/save response is `{record}`. Mutation JSON is `{expectedVersion,document}`; create omits version. Action JSON is `{expectedVersion,revisionId?}`. Stable errors:400 validation,401 session,403 capability,404 absent,409 conflict,413 size,415 type,503 backend.

Database RPC contract (all parameters named): `admin_list_records(p_kind,p_query,p_limit,p_offset)`, `admin_get_record(p_id)`, `admin_save_record(p_id,p_kind,p_expected_version,p_document)`, `admin_transition_record(p_id,p_expected_version,p_action,p_revision_id)`. Record DTO: `{id,kind,title,slug,document,version,publishedRevisionId,archived,updatedAt,revisions?}`; list items omit document/revisions. Document common fields: `title`, `slug`, `summary`, `blocks`, `seoTitle`, `seoDescription`; kind-specific fields are strictly allowlisted. All user text/URLs/arrays and total bytes have limits. SQL repeats authorization/version/integrity checks even for direct SDK callers.

Additional typed operations for variant prices, inventory, media and inquiries are documented by their implementation/test evidence. Admin UI uses the selected Superdesign sidebar/topbar, compact tables and editor panels; mock prototype metrics and fake records are omitted. Full public storefront layouts remain Phase4, but published-data endpoints and basic published rendering must prove that admin changes take effect without deployment.
