# Phase 6 non-commerce recovery readiness

Audit date: 25 October 2026. This is a read-only recovery assessment and operator runbook for the existing Clerk + InsForge non-commerce application. It does not provision production, create a backup, export customer data, change billing, create a branch, restore data, send mail, or deploy. Checkout and payment recovery remain out of scope.

## Findings and current limits

- The linked InsForge project is the development project recorded by the phase evidence. A read-only `backups list` against the linked Pandabyte project returned an empty inventory. No backup was created or restored during this audit. This confirms only that the CLI inventory showed no backups; it does not prove the absence of every provider-managed recovery point.
- The installed official InsForge CLI guidance documents `backups list`, `latest`, `create`, and `restore`. It also documents `db export` for schema and/or table data. No export was run: a full export defaults to all tables and data and could contain private customer, address, inquiry, role, and audit records. `backups latest` can print a presigned download URL, so do not paste its output into logs, tickets, or chat. The CLI guide documents Cloud restore as overwriting database and storage; for self-hosted instances it documents database-only `pg_restore --clean`, which leaves later-created tables and storage untouched. [Official CLI backup guidance](https://github.com/InsForge/insforge-skills/blob/main/skills/insforge-cli/SKILL.md), [official database export reference](https://github.com/InsForge/insforge-skills/blob/main/skills/insforge-cli/references/database/export.md).
- The project has a prior private schema snapshot and migration history for review, but the Phase 2 record says the CLI schema export returned text in JSON mode and did not write the requested output file. A schema snapshot is not a data backup, a storage-object copy, or evidence of a successful restore. See [Phase 2 recovery notes](phase-2-access.md).
- Application files use two InsForge buckets: `private-account-files` for customer uploads and `editorial-media` for editorial media. Their objects are separate from PostgreSQL metadata. Phase 3 and Phase 4 operations both state that no database-plus-storage restore drill has been performed. A database-only snapshot cannot establish file recovery.
- A read-only catalog aggregate in this checkpoint reported RLS enabled on all 27 public tables. That verifies the flag only; it does not establish effective grants, policy coverage, or role-specific access after restoration. The restore acceptance checks below must include real signed-out, customer, cross-customer, and staff access tests.
- Clerk remains the sole identity provider. Application ownership and staff membership records store opaque Clerk subjects as text; InsForge Auth IDs, email matches, and user-editable metadata are not alternate identity keys. The protected owner ADMIN membership and capability materialization are database state and must remain bound to the same verified Clerk subject. See [admin-role contract](admin-roles.md).
- Recovery objectives, database/file retention, production operator identity, and production restore checks are still unapproved. No production project has been provisioned or deployed. The development evidence is not production assurance.
- The local InsForge CLI guidance says Cloud restore overwrites the current database and storage, while InsForge's public [Backup & Restore announcement](https://insforge.dev/blog/insforge-backup-and-restore) describes restoring the project database. Confirm the precise behavior and blast radius for the selected project in current provider documentation or a disposable target before any production restore. Until confirmed, treat restore as a destructive whole-project overwrite. The announcement listed one manual backup and no daily automatic backups on Free when published; verify today's entitlement in the project before relying on that historical plan description.
- A broad server-only `INSFORGE_EDITORIAL_STORAGE_READ_KEY` is used for a constrained published-media read because the managed storage schema denies the needed public grant. Its scope, access, rotation, and isolation remain operational risks; keep it out of client bundles, exports, logs, and this runbook. See [Phase 3 operations](phase-3-operations.md).

## Operator runbook

Use this only after the owner has approved the target, recovery point, operator, and any destructive action. Keep exports, manifests, identity mappings, and provider diagnostics in an encrypted, access-controlled recovery location; never place them in Git, issue text, screenshots, or general logs.

1. **Declare and scope the incident.** Record incident owner, UTC start, affected environment, suspected failure window, and whether the issue is limited to code, a database record set, storage objects, or provider identity access. Use bounded application diagnostics from [the operational contract](operational-diagnostics.md); retain only allowlisted event class, area, status, time, and response reference. Do not collect raw customer requests, provider payloads, tokens, or database/session identifiers in the incident record.
2. **Stop writes and validate the target.** Use the hosting/provider's approved maintenance or access-control procedure; this repository has no verified recovery-mode switch. Independently verify that every CLI/dashboard action points at the intended environment. Do not infer production identity from a project name or copy development credentials into production.
3. **Preserve the pre-recovery state.** Before a restore, capture a new provider backup if the project supports it, plus a separately protected database schema/migration-history record and a storage inventory/copy. Record creation times and checksums without printing object contents or customer fields. Keep the pre-restore snapshot until the recovered service passes acceptance; no retention deletion is authorized by this runbook.
4. **Choose the narrowest safe repair.** Prefer a reviewed forward code or additive migration repair when data can be preserved. Use a full provider restore only when its exact scope is confirmed and its data-loss window is accepted. Do not import a full data export, reset a project, replay an applied migration, drop tables with `CASCADE`, or use a development fixture cleanup against real customer data.
5. **Restore PostgreSQL and preserve migration history.** In an isolated recovery target, compare the backup's schema and applied migration history with the versioned `migrations/` directory and the deployed application commit. The official migration CLI supports listing/fetching applied history; inspect and reconcile before applying anything. Applied migrations are historical records: do not edit or replay them as rollback. If the snapshot predates a required schema, make a reviewed forward-only plan and apply only the explicitly reviewed pending migrations. Do not run `up --all` blindly. [Phase 3 recovery rules](phase-3-operations.md), [Phase 4 migration rules](phase-4-operations.md), [official migration overview](https://insforge.dev/blog/insforge-database-migrations).
6. **Restore storage separately and keep it private.** Confirm the exact bucket/key inventory and copy `private-account-files` and `editorial-media` through a provider-supported file backup/restore path. Preserve object keys, byte content, and the existing private access policies. Do not make either bucket public. Reconcile customer-file metadata to the exact owner subject/key and reconcile `editorial-media` objects to media metadata and live revision references. Restore only keys proven in the approved manifest; do not bulk-download customer files for manual review. The [InsForge S3 gateway announcement](https://insforge.dev/blog/insforge-storage-s3-gateway) documents S3-compatible access, but a separate object copy and restore procedure still needs project-specific verification.
7. **Preserve Clerk identity bindings.** Confirm the restored application is configured for the intended Clerk instance using the protected server configuration names in `.env.example` (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`) without revealing their values. Sign in through the existing verified Clerk account and validate that the server-derived subject resolves to the same InsForge records. Never create a replacement identity or rebind records just because an email matches. If the original Clerk subject cannot be verified, stop role restoration and require owner/provider-assisted identity recovery. Restore the protected owner ADMIN only against the verified existing subject using the restricted operator recovery path; never use an application email allowlist or metadata claim.
8. **Validate before reopening writes.** Compare bounded row counts and invariants without exporting record contents. Confirm: current migration history matches the selected application commit; role membership and capability rows agree; the protected owner remains ADMIN; customer profiles, addresses, and file ownership stay private; both buckets remain private; object keys match their metadata; published media references resolve; inquiry/outbox state is preserved without converting unknown delivery outcomes into retries; and public catalog/company reads expose only published projections. Run signed-out, customer, cross-customer, and authorized staff access checks with disposable fixtures only. Verify critical browser journeys, CSP, and safe diagnostics. Do not alter owner or customer data to make a check pass.
9. **Resume and record evidence.** The incident owner signs off the exact restore point, measured elapsed recovery time, observed data gap, validation results, and remaining discrepancies. Reopen writes only after those checks pass. Keep the restore snapshot, object manifest/checksums, migration comparison, and approval record in the protected recovery location for the owner-approved retention period.

3. Resolve the CLI/provider description of Cloud restore scope for the selected project and rehearse the exact operation in an isolated target.
4. Perform a database-plus-storage restore rehearsal, then test Clerk-subject continuity, protected ADMIN access, RLS, private file isolation, published media, and migration alignment.
5. Approve RPO/RTO, recovery location, operator ownership/approval, and an emergency path if the owner's Clerk account is unavailable. Preserve role and capability audit records and their verified subject bindings during recovery.
6. Verify production Clerk/provider configuration and the broad editorial storage credential's access/rotation design before deployment. See [security readiness](security-readiness.md), [Phase 3 operations](phase-3-operations.md), and [Phase 4 operations](phase-4-operations.md).
