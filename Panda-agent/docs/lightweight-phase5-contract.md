#### Agreed private image wire

All four routes are POST: `/v1/images/upload`, `/v1/images/status`, `/v1/images/read`, `/v1/images/delete`. Upload is raw normalized PNG at most 2 MiB; controls are strict JSON exactly `{version:1,threadId,assetId}`. No external URL, base64 image JSON or client filename/path. The existing literal base64url-claims HMAC mechanism uses a separate audience **`panda-image-v1`**, actions **`uploadimage`**, **`statusimage`**, **`readimage`**, **`deleteimage`**. Claims have exactly **16 keys**: `v`, `aud`, `action`, SHA-256 `sub`/`sid`, `threadId`, `assetId`, `bodySha256`, **`imageSha256`**, `mediaType:'image/png'`, integer `width`, `height`, `bytes`, **`expiresAt`**, `exp`, and UUID `nonce`. Bind the exact raw request-body hash separately from normalized-image hash. Reject extra/duplicate fields, boolean-as-integer, malformed Unicode/UUID/hash, wrong audience/action/body and replay. Capability expiry is at most 60 seconds from the current runtime clock; a new upload's asset Unix expiry is future and at most 900 seconds, or the explicitly scoped shorter operator fixture. Fresh controls retain the original asset expiry and cannot extend it. `expiresAtUnix` is not a wire key.

For uploads `bodySha256` and `imageSha256` match the normalized PNG. A control body hash instead hashes its own JSON while `imageSha256` remains the original normalized image hash: the worker must match immutable stored asset metadata and verify stored file bytes before reading; BFF independently compares returned PNG SHA-256 to the authoritative InsForge normalized hash. No changed upload digest may reuse a ready/pending/deleted asset identity. Signed dimensions/bytes/hash/expiry must match the stored row. Foreign owner/thread status/read yields missing, never an existence disclosure.

Every authenticated JSON or PNG response has header **`X-Panda-Image-Receipt`**, a **hex HMAC-SHA256** over exact bytes: `'panda-image-response-v1\n' + nonce + '\n' + decimalHttpStatus + '\n' + SHA256(rawResponseBody) + '\n' + exactContentType`. This image receipt is **not** the evidence/guide base64url receipt. Content-Type is exactly `application/json` or `image/png`. PNG reads require the exact permitted image content type, byte cap/hash and receipt; JSON responses require their strict union/content type and receipt. HTTP status/content type are cryptographically bound rather than inferred from a cached body. The BFF provides the real normalized upload and owned DB reference, retains raw-body/response limits through consumption, and checks current session/ownership/expiry before public release. It never exposes private capabilities or a worker URL. Unauthenticated responses need not have a receipt.
