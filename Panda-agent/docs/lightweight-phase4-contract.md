## Agreed implementation amendment — exact guide wire and fences

These concrete decisions supersede the earlier review-only suggestions above. Thread UUID is the project boundary. ### Public input and project state

The existing messages route accepts a strict disjoint union: the current QA body, or exactly:

```json
{"requestId":"canonical UUID","guide":{"goal":"student goal","board":"one catalog board hint","components":["user-reported component"],"expectedVersion":0}}
```

Guide has exact keys `goal`, `board`, `components`, `expectedVersion`, with optional `revision`. Reject simultaneous `question`/`webSearch`, extra keys, duplicate JSON keys, malformed Unicode, invalid types and the existing 8,192-byte public body limit. Trim scalar fields once before canonical hashing; preserve the resulting canonical input for idempotency. Lengths use UTF-16 units: goal 1–600, board 1–128, optional revision 1–80, components 0–8 nonempty strings of at most 80 each. Repeated component strings are permitted as bounded user reports; they add no authority, tool calls or worker count. `expectedVersion` is a nonnegative safe integer, 0 for no prior memory. The request UUID is the existing turn identity, not an access capability. Server derives the bounded display question from the canonical intent and resolves **one** current catalog board; conflicting/unknown identity clarifies without claiming a factual guide.

Project memory stores owner/thread, monotonically versioned intent (same bounded goal/board/revision/components), at most eight unresolved question strings of at most 160 units, successful guide count, compaction count and at most seven recent goal strings of at most 600 units. No evidence passages, quote/citation list, source proof or model-generated board fact is memory authority. Student-supplied strings remain explicitly unverified intent. A genuine completed guide atomically updates protected history and memory/version/count once; cancelled, stale, disabled or unavailable fixed terminal notes do not increment memory or compaction.

On every eighth successfully completed guide, fold recent goal context into the latest bounded structured intent/questions and clear the recent-goals list, recording the compaction count/boundary. Preserve the current student's goal and unresolved questions, retain original chat history, and refresh factual evidence for subsequent runs. This must be an actual bounded-state fold, not merely a counter labeled compaction. Other successful guides append only the bounded current goal to the at-most-seven recent list. Expected-version compare-and-set is serialized under the owner/thread lock; replay of an admitted request uses its original intent/version and never mutates memory again.

Expose the owned memory version/intent through a bounded owner-scoped project-state read for the guide form/reload; Root chooses the route within existing ownership conventions before UI wiring. Public state contains no actor IDs, private turn records, grants, source handles, source proof or raw worker result. Adding project state must not change the ordinary messages/SSE DTO contract implicitly.

### Exact private request and response

Private guide endpoints are `/v1/guides/run`, `/v1/guides/status`, `/v1/guides/cancel`. Capabilities use **`aud:"panda-lightweight-guide-v1"`**, with actions **`runguide`**, **`readguide`**, **`cancelguide`** respectively. Retain the exact existing HMAC literal-claims/raw-body scheme, actor/session/turn/SKU hashes, expiry ≤60 seconds, one-use nonce and response receipt construction. Raw body hash binds the thread/project, skill and intent. Wrong audience/action/kind cannot cross into evidence execution or accept its cached output.

Run body has exactly:

```json
{"version":1,"mode":"deterministic-guide-v1","threadId":"canonical UUID","turnId":"canonical UUID","productSku":"server-resolved SKU","skill":{"id":"embedded-project-guide","version":1,"hash":"64 lowercase hex"},"intent":{"goal":"student goal","board":"board hint","components":[]},"fragments":[]}
```

Intent optionally contains `revision`; no other field. Skill version is an exact supported positive integer and hash must equal the reviewed bundled version; no request-supplied source/package/code. Thread/turn/SKU/intent must match admitted BFF metadata. Status/cancel use exact `{version:1,threadId,turnId,requestBodySha256}` with the **original run-body digest**, through the distinct guide endpoint/audience/action. The journal binds the project/thread as well as actor, turn, kind, SKU and digest. The BFF derives all values from the owned admitted record, not browser control JSON. Keep the same 98,304-byte raw-body, ingress, queue/deadline and private 16,384-byte response limits.

Guide alone permits **0–8** exact `{handle,text}` fragments under existing per-fragment/20,000-unit bounds. Trusted TS includes only currently eligible canonical text; atomic fact extraction must have complete eligible coverage, not hide conflicting low-ranked chunks. If no eligible sealed evidence is available or complete context cannot fit, an explicitly conceptual guide may receive zero fragments. Then **selections and citations must be empty**, with visible no-approved-facts/unverified labels; no candidate widening or substituted source. Catalog resolution is not evidence of wiring/revision/interface capability.

Complete HTTP 200 body is **exactly**:

```json
{"version":1,"state":"complete","guide":{"template":"parking-monitor","questions":["revision","wiring","framework","component-specifications"],"nodes":6,"workers":2},"selections":[{"handle":"supplied handle","quote":"exact literal quote"}],"usage":{"modelCalls":0,"inputTokens":0,"outputTokens":0,"costNanoUsd":0}}
```

`guide.template` is only `parking-monitor` or `project`. This first implementation always returns all four shown question IDs in that exact order; no arbitrary strings or Markdown. Nodes/workers report the actual fixed six executed graph nodes/two bounded read-only task workers; incomplete/deadline runs cannot invent these counts as success. This implementation narrows selection to 0–1 exact atomic MCU-field quotes, under the existing 600-UTF-16-unit literal bound, with no source URL from the worker; zero fragments requires zero selections. It does not establish GPIO, power, sensor compatibility or framework facts. Usage is four exact integer zeros in runtime and TS validation. Existing strict noncomplete states/codes/statuses, including authoritative `cancelled`, apply to guide routes without broadening output acceptance.

The six-node graph coordinates two independent tasks (bounded evidence selection and conceptual outline), joins and verifies, with no recursive delegation or second TS graph. One shared 30-second deadline, one active/four queued/per actor one and shared durable journal admission cover the whole run. Reuse the actor+turn primary key and original digest; add a persisted execution-kind binding so guide/evidence caches, delayed selects and tombstones cannot be reinterpreted across modes. Keep existing status-only recovery and authoritative pre-admission/queued cancellation; dispatched unknown work is not silently retried or described as canceled upstream.

TS renders the reviewed pinned skill-version template from these enums plus validated current source DTOs and **escaped/labeled user intent**. It never accepts worker Markdown, URLs, factual free text or memory instructions. Escape user-provided Markdown/citation markers to avoid presenting a student's text as sourced claims. Admission atomically binds canonical input/hash, workflow kind, owner/thread/request, expected memory version, pinned reviewed skill ID/version/hash and **activation epoch**. Lock order is consistent across admission, management and completion. New QA admission/final save checks its own QA skill gate without adding a guide worker call or changing QA factual semantics. Disabling guide does not disable independent QA. Every disable/re-enable/switch/rollback increments the relevant activation epoch; disabling then reenabling the same hash cannot revive an older dispatched result.

Idempotent admission checks an existing request/canonical input **before** rejecting a changed current memory version, so replay never creates a second run or repeats memory updates. Complete replay returns the source-fenced saved history; pending replay is status/control only, with the original pinned metadata/digest. No current registry/expectedVersion change grants redispatch of an old turn.

Guide preparation records the original signed run-body hash and current factual scope hash (or explicit no-facts conceptual state) under durable CAS. Before context/prepare, refresh current owner/session, registry/grants/epoch and evidence. Finalization atomically locks/rechecks current actor/thread/request, HMAC expiry after locks, expected project-memory version, pinned reviewed skill/hash/activation epoch, current canonical scope and literal citations; only then stores one protected answer and increments memory/guide/compaction state. New forward migrations only; no edit to applied Phase 2/3 migrations.

**No stranded-project regression:** if current skill/grant/epoch changed or source facts became invalid while a guide ran, SQL discards the buffered guide/facts and derives a fixed **no-quote terminal note**, protects its hash and makes no memory/version/count update. Late worker results cannot replace that note. It does not claim upstream cancellation or success and never releases stale facts. Current ownership/session/final safe read still apply; it is not an auth bypass. Already saved history remains current-source-fenced; a later execution disable need not erase historical user intent. Unknown dispatch/cost or missing authoritative continuity remains honest and is not a license to replay.
