# Phase 6 retrieval preflight

6 November 2026. This is a source-only inventory and proposed interface boundary. No source, database, provider, runtime, dependency, or cloud state was changed or queried. Phase 5 is the last passed phase; a proposal here is not Phase 6 acceptance.

## Current customer path and the gap

`src/server/lightweight-handler.ts` owns chat admission, cancellation, status and public release. It calls `createLightweightAnswer` in `src/server/lightweight-answer.ts`, which resolves one catalog product, obtains its current `store.scope`, and passes the actor's genuine user-scoped InsForge client to `answerWithLightweight` in `src/lightweight/evidence.ts`. That adapter uses `answerQuestion` and `createInsforgeAdapters`; no global client is an acceptable substitute.

`answerQuestion` in `src/retrieval/answers.ts` parses one bounded question/SKU/revision, validates eligibility before ranking, limits selected whole fragments to eight/20,000 UTF-16 units, verifies handles and literal quotations (at most four, each at most 600), and rechecks the scope before and after selection. The adapter in `src/retrieval/insforge-adapters.ts` checks the `engineering-proof.ts` candidate/config/manifest and per-product membership, chunk hashes, generation, blocked IDs, source provenance and current actor-scoped RPC responses. Historical engineering hashes are not present-day rights or source approval. Missing identity, physical revision, board wiring, unsafe claims or conflicting scope stay clarification/insufficient/unavailable, never guessed.

`src/lightweight/client.ts` and private `services/lightweight/lightweight/app.py` bind one turn, one product SKU, one body hash and a short-lived actor/session capability to selection, signed response receipt and status/cancel. The deterministic MCU profile requires complete eligible scope and reports zero model calls; it is the existing single-question fast path. `src/server/lightweight-store.ts` persists one product ID/SKU/scope hash and one digest, and `migrations/20261105090000_panda-agent-lightweight-turns.sql` fences citation currency and product scope at protected save and replay. Read recovery reconstructs the identical body and calls status only; a lost or ambiguous execution is not dispatched again. The private journal is likewise keyed by actor/turn and binds one original body. Current `resolveChatScope` explicitly returns conflict for multiple named products.

Consequently, repeatedly calling the present selector with the same turn ID for separate needs or combining multi-product citations in the present one-product finalizer is not a valid compound implementation. A new bounded composite plan, one coherent scope-set binding and protected save/read/replay fence must be agreed before that path can claim two-source support. Keep the existing simple MCU route and wire unchanged. `src/diagnostics/tool-broker.ts` is a narrowly scoped optional external-document broker, not the canonical RAG capability broker. Do not claim an existing standalone MCP server is mounted in this checkout.

## Reference source, not production reuse

The original checkout contains `Panda-agent/src/retrieval/multi-product-identity.ts` and `product-context-set.ts`, and `control-room/rag-workflow.ts`. They are useful for design review: the context helper collects per-product passages and fingerprints and revalidates identity/current scopes, while the Admin workflow keeps private passages out of graph state. These files are not present in the current lightweight checkout or a customer authorization/persistence contract. In particular the old identity planner treats some `or` forms as comparison, and its Admin graph/context proof has different callers, limits and dependencies; copying it wholesale would violate the proposed ambiguity boundary. It is not evidence that the current single-product SQL finalizer can save a multi-product answer.

The original checkout also has `Panda-agent/services/rag-mcp/broker.ts` and `http.ts`, called by `src/server/native-rag-selector.ts`. Its in-process `createRagBroker` binds subject/chat/runtime epoch/session/turn/question/product/revision, expiry and prevalidated fragments; it mints a one-use opaque capability and opaque handles, validates exact output/quote membership, and calls injected current authorization, source revalidation and `verifyExecution` before release/finalization. The original native selector obtains those callbacks from a separately admitted native execution/receipt authority; the opaque handle or a syntactically valid capability alone is not a receipt or a current grant. The adapter's response is limited to 12 KB and one invocation. It is absent in this checkout and is tied to a legacy native-selector caller; Phase 6 may review/adapt its small broker contract and tests in process, but must provide genuine current callbacks and a receipt authority compatible with the lightweight turn. Do not reintroduce its OpenCode executor, relay or native container as a fallback. Multi-need use also needs a new explicitly bounded scope/capability design, not an unreviewed relaxation of its one-use semantics.

## Proposed finite controller for contract review

Route only explicit supported shapes to an optional deterministic controller; all other questions retain the established path. A finite plan contains one to three evidence needs, each an exact requested field and one independently resolved product or reviewed document scope. `AND` with explicit uniquely resolved products and explicit `compare`/`versus` between uniquely resolved products may be planned; an `OR` selection, missing product, shared alias, revision conflict, or unclear comparison asks a clarification before fetching. Do not infer a compatibility verdict, board header mapping, physical wiring, voltage tolerance or tested code from a product name or chip document. Return insufficient when an eligible source does not directly establish a requested field.

Before any call, freeze the plan, selected skill/version and permission subset, actor/thread/turn, target products, revision/framework, ordered need IDs, and a shared 30-second deadline. Charge every canonical lookup and optional authorized external lookup to one maximum of four tool invocations; permit at most one bounded reformulation, no retry after unknown external or execution outcome, and at most two concurrent read-only tasks. Selection and answer construction remain deterministic with zero model calls. Count status reads distinctly from new execution. Treat source passages and pasted text as untrusted data, and do not send user logs or private context to an external tool. A separately approved search/fetch capability can return only a labeled dated external reference; it is not a canonical citation or proof of board wiring.

The Root/Sol contract needs an atomic durable representation of the ordered needs, each authoritative product/source version and scope hash, planned request hashes, selected skill epoch, capability IDs, budget consumption and terminal/unknown states. It must bind the complete request to the same actor and turn, retain one-use per-call authority and receipts where private execution is used, and define crash/status-only reconciliation without redoing an ambiguous invocation. Preserve one protected terminal answer and prevent cross-workflow ID reuse. At final commit and every safe history/replay read, revalidate the *entire* scope set, literal quote-to-source binding, owner/current session, skill/tool epochs and grants under appropriate database locking; a changed/withdrawn source must suppress the affected historical quote or replace it with a fixed no-quote terminal outcome. Never weaken the existing one-product predicate as a shortcut. Citation identity must remain source-specific and collision-free after merge, with limits applied across the whole answer, not once per subcall.

## Registry, helper and corpus inventory

- `migrations/20261105090002_panda-agent-guides-skills.sql` restricts `panda_agent_skills.id` to `product-evidence-qa` and `embedded-project-guide`; `src/server/skills-api.ts` independently allows the same two IDs. Existing versions and Admin review/enable/disable/rollback use expected-version checks, current ADMIN and audit events; guide and QA admission/finalization bind their existing epochs. The requested `panda-documented-firmware-help`, `panda-error-triage` and `panda-project-planner` therefore require a new reviewed forward migration, bundled skill records and API/reader/trigger changes, not just Markdown files. Trigger selection cannot grant a capability: effective permissions must be the intersection of the reviewed skill, current server grant and the request-scoped plan. Existing skill epochs and histories must remain valid.
- No general typed unit-conversion or deterministic BOM-formatting helper was found in the current `Panda-agent/src` inventory. `src/guide/answer.ts` formats a conceptual BOM from user-declared inputs; those entries are explicitly unverified and it is not a general converter or compatibility checker. New finite, dimension-checked, finite-value/overflow-bounded local helpers may format user-provided data, but cannot establish sourced engineering properties.
- `engineering-proof.ts` is a historical source-visible sealed engineering membership with a 284-member manifest and per-product digests; the runtime adapter still requires live, actor-scoped product/scope responses. Historical Phase 2/4 handoff records show an x8266 MCU citation and a separate xLoRa guide workflow, but do not establish that two currently eligible independent documents support any particular comparison. The only reviewed Phase 5 vendor catalog entry is the pinned ESP-IDF ESP32 GPIO page; its exact approved directive and current withdrawal/approval must be checked at execution, not inferred from this document. Synthetic retrieval tests such as `tests/retrieval-answers.test.mjs` prove guard behavior only, not current real-document coverage. No corpus contents or private fixture were copied here.
- The existing Control Room intake accepts quarantined PDF/MD/TXT, but PDF handling is a signature check and there is no extraction/parser/OCR or reviewed promotion worker (`docs/control-room/backend-contract.md`). This is an actual extraction gap for an authorized PDF intake, not proof that a specific currently approved Phase 6 source needs PDF extraction. MarkItDown remains OFF until an identified approved input requires it and its isolated on-demand parser/dependency/hostile-file review passes; it must not become a customer tool or grant retrieval rights.

## Evaluation and focused gates

`src/control-room/insforge-store.ts` registers `engineering-listings-v1` as 20 source-visible cases with `heldOut:false`; the Admin evaluation endpoint is unavailable, not a running held-out evaluator. Construct a separately governed held-out set without placing gold answers into ingestion, prompts, source documents, selector examples, logs or customer DTOs. Freeze the corpus/scope identity and case partition before evaluation; split by product/document and paraphrase family rather than merely duplicating question wording. Include explicit two-product AND/comparison, ambiguous OR/shared alias, partial coverage, wrong product/revision, conflicting source, malicious instruction, withdrawal after selection/save and unavailable tool cases. Label synthetic tests, source-visible engineering cases and independently authored held-out cases separately.

Run Phase 2 baseline and candidate on the same frozen cases, scope/flags and environment; do not treat the Phase 2 single-MCU success as a multi-hop baseline. Report denominators and per-case outcome for answer support and literal citation correctness, correct abstention/clarification, wrong-product leakage, source-revocation leakage, tool executions, status reads, model calls and cost, along with end-to-end p50/p95 only when the sample is large enough to interpret. Include one-need fast-path regression and no double-dispatch/one-save recovery; require the exact observed zero model/paid calls rather than assuming them. Unit fixtures, actual authorized development APIs, real official-tool fetches and browser evidence must remain separately labeled. No benchmark result or live coverage claim is made by this preflight.
