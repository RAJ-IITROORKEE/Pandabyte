## Existing direction and critique

Keep the existing Panda Agent workspace and its one assistant-ui external-store runtime, saved-message stream, source cards, composer and navigation. Keep the Admin shell, Outfit typography, scoped green/neutral light and dark tokens, existing controls and the exact PandaByte logo. The RAG Control Room's existing source review is the visual and interaction anchor for skill administration. No new logo, theme, dashboard or marketing-style illustration is needed.

Three gaps drive this small addition: the current composer does not distinguish an ordinary question from a project guide; it has no visible, owner-scoped project memory or version conflict state; and Control Room intake review does not implement skill versions, activation or rollback. The design must make the user's current choice, the project's reported facts and the Admin's active version legible without implying any of them is verified hardware evidence.

## Student project guide

Offer a clearly labeled, optional **Project guide** entry beside the existing composer actions. Ordinary product chat remains the default and retains its current behavior. Selecting the guide opens a compact labeled form within the same workspace, with goal, board/model, optional physical revision and declared components. The form supports empty and partial values with targeted prompts for missing or ambiguous details. Explain that student-supplied revision and components are unverified. Avoid a second conversation surface, independent history, generated tokens or automatic submission.

Once a project exists, show a concise current project summary with explicit server-returned version and an edit action. Server-owned memory contains bounded intent and unresolved questions, not source text or a grant to reuse old facts. Edits carry the displayed version; a conflict preserves the local edit, shows that the server version changed, and offers an explicit reload/review action. Loading, no project, unavailable, validation, save-in-progress and unknown outcome each need honest status; do not automatically replay a write. The exact field bounds and request names come from the agreed wire contract.

The agreed messages request is a strict union: the existing question path, or `{requestId, guide:{goal,board,revision?,components,expectedVersion}}`; guide requests do not include question or web search. The goal is at most 600 characters, board 128, optional revision 80, and at most eight components of 80 each. Memory exposes its version, current intent, at most eight bounded open questions and at most seven recent goals. The eighth successful guide folds current intent and questions and clears recent goals; saved chat history remains intact.

Render the resulting saved guide through the existing message and citation components: objective; confirmed versus user-reported components; conceptual architecture; supported versus unverified interfaces; firmware outline; verification steps; open questions; current citations. Use existing source disclosures. Clearly identify unverified wiring, pins, power and compatibility as placeholders when current evidence does not support them. A supplied board revision is not proof; no simulated compile, test, model or hardware claim. Progress is limited to genuine server stages and saved text appears only after current checks and durable save.

## Admin skills

Add a **Skills** section inside the existing Control Room, not a new Admin identity or public settings surface. The server independently checks a current genuine ADMIN membership for every read and mutation; navigation visibility is not authority. List only server-allowlisted bundled descriptors with a clear enabled/disabled state and current reviewed version. Never display internal subject IDs, secrets, source paths or private prompts. Do not offer upload, arbitrary skill text, installation, tool grants or editable runtime budgets.

Selecting a skill exposes its immutable version history and review state. An Admin can inspect the server-supplied provenance/version information, review an eligible version, enable or disable a reviewed version, and select a previously reviewed version for rollback. Each state change requires a reason and current expected version. Use the established labeled form/dialog, busy guard, dismissible notices and version-conflict reload/review pattern. A conflict or unavailable/unknown outcome never becomes a success notice or silently retries; retain meaningful local input until the Admin explicitly reloads. State changes and rollback are real server operations with audit history, not cosmetic toggles. Disabling guide affects the next guide run but does not turn off ordinary product chat. The agreed server contract defines in-flight behavior and authoritative outcomes.

## Accessibility and verification

Use semantic labels, headings, native buttons and disclosure controls; associate validation messages to fields, expose genuine progress and errors through appropriate status/alert semantics, and return focus after dialogs or interrupted operations. Keyboard-only users must reach opt-in, fields, save/cancel, source expansion and version actions. At narrow widths, forms stack and long history/version content remains readable without page-level horizontal overflow. Check light/dark contrast and reduced-motion behavior using the existing scoped styles. Keep drafts and conflict/access guards when notices are dismissed.

Before implementation, complete the applicable Superdesign design-first workflow and inspect the resulting actual canvas/draft; this document is not a canvas or approval. Verify the final implementation in Codex browser with a real authorized Admin and a genuinely denied non-Admin, a disposable project and skill transition/rollback, guide disabled and ordinary chat still working, current citations and placeholders, long-thread compaction/reload, keyboard/focus and small viewport. Record fixture and real-browser evidence separately; unavailable backend or missing actual design review remains an open gate.
